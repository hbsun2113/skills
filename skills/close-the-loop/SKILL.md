# 闭环交付

把完成定义为“实现加因果证据”。在内部安静地执行本协议；只有当决策、变化后的验收门槛、阻塞项或残余风险对用户重要时，才将其呈现出来。

按闭环风险选择路径，并按以下优先级判定：

- **完整路径（full path）优先：** 只要变更跨越信任或持久性边界、改变外部或有版本约束的兼容性承诺、修改多个消费者共享的状态，或可能在时序、中断、生命周期、迁移、特定目标环境中失败，就走完整路径并使用闭环账本和相关诊断。内部导出或用户可见标签本身不构成公共契约。
- **轻量路径（light path）：** 未命中完整路径触发器，且变更可逆、局部、确定、只有一个责任方、不涉及共享契约或生命周期行为，并存在明显聚焦检查时，检查、修改、验证、报告即可。跳过闭环账本、诊断和独立冷审。
- **标准路径（standard path）默认：** 未命中完整路径触发器、但不能同时满足全部轻量条件时，追踪受影响路径和责任方，完成范围内修改，并运行聚焦检查及相关的最小回归检查；默认不使用账本、完整诊断或独立冷审。只有新证据暴露完整路径触发器时才升级。

仅对完整路径工作，在内部维护一份精简的闭环账本：

`已观察路径 -> 验收门槛 -> 变更 -> 证据 -> 残余项`

不要把账本变成仪式；它只用于暴露尚未闭合的环节。

## 1. 追踪真实运行系统

从当前故障信号、请求、事件或状态转换开始，沿代码追踪到实际拥有该效果的组件、所有消费者和恢复路径。

选择改动前，检查当前实现、契约、测试、配置和目标环境。把旧补丁、计划、工作日志和注释视为证据，而不是仍然可靠的地图。架构已经移动时，基于现状重新推导改动。

区分已观察事实、推断和未知项。当因果路径、责任边界、受影响消费者和实质性未知项都已识别后，停止扩散式探索。对于资源生命周期变更，即使缺陷报告只提到正常关闭，资源如何被排他认领、所有权信号保存在哪里，以及所有选择同一批所属资源的 teardown、recovery 和 sweep 路径，都属于真实运行路径。

## 2. 将风险转为验收门槛

走完整路径时，明确工作闭环后必须有哪些可观察事实。走轻量路径时，请求的行为加一个聚焦检查即可。完整路径的门槛应从失败模式推导，而不是从待编辑文件推导：

`风险 -> 保护机制 -> 可证伪检查`

覆盖相关的成功结果、拒绝或失败结果、恢复行为、回归面和非目标。将需要人工操作或当前不可用环境的检查，与代理能够实际运行的检查分开标记。

对完整路径，至少选择一个与当前风险相关的**前置条件碰撞**和一个**中断边界**作为反例。前置条件碰撞用于推翻“输入一定规范、标记一定唯一、值一定可复制、路径一定是普通文件”等隐含假设；中断边界用于推翻“计数、检查点、所有权或状态已经持久化，因此外部效果必然发生”的错误等价。只在相关时选择，不能用无关反例凑数。

当证据改变认知模型时，修订验收门槛。不要为了表面一致而保留过时计划，也不要添加无法改变交付决定的清单项。

## 3. 在责任边界修复

把不变量放在最接近实际效果的责任边界（owning seam）：状态所有者、传输层、持久化边界、共享契约或资源生命周期所有者。优先做一个真正承重的修复，而不是只给部分调用方打补丁。

替换高风险机制时，先建立清晰边界；在新路径得到证明期间，只保留安全且确有必要的既有行为。不要仅为了并存兼容而保留违反安全、完整性或验收门槛的路径；先保护或禁用它。追踪变更后共享状态或契约的每个已知消费者；另一个消费者仍能进入同一不安全路径时，单点修复并不完整。

认领外部资源时，使用排他创建、原子登记或等价机制证明资源由本次操作创建或合法接管；不要先执行可能无操作的 `add`、create 或 mkdir，再把同路径既有对象标记为己有。认领失败必须保留外部对象并暴露冲突。

只有每层防御都有明确且不同的职责时，多层防御才有价值。若重复检查可能绕开同一个缺口并一起漂移，不要把它们称为纵深防御。

## 4. 约束并暴露失败

区分不存在与失败、预期拒绝与畸形输入、瞬时失败与永久失败。不要把 I/O、解析、认证、传输或持久化失败转换为空值或表面成功。

当数据或工作不可信、受外部控制或会不断累积时，在分配或累积前施加相关边界：输入大小、缓冲区、队列、重试、等待和资源数量。在有限退避或长操作期间，保持取消和清理路径可用。对本就有界且确定的工作，不要凭空增加任意限制。

当宽松回退会暴露授权、隔离、机密性或持久完整性时，采用故障时拒绝（fail closed），并提供可观察的恢复路径。其他场景应明确失败，而不是机械地拒绝服务。让原始错误信号传播到足以诊断根因的位置。

## 5. 验证状态转换，而非只有稳态

选择可能破坏变更契约的时间轴场景：乱序完成、重复执行、重试、取消、部分失败、重启、重放、重连、并发访问、清理，以及中断后的恢复。

对于有状态工作，只验证因果路径实际涉及的转换。当中断或重排是实质性失败模式时，先建立前置状态，再跨越转换，在过程中中断或重排，随后恢复，并断言最终状态以及不存在陈旧或泄漏状态。若 recovery 或 sweep 用于进程崩溃、重启或所有者重建后的恢复，让所有权信号跨越同一失败边界，并在测试中重建所有者或清理器后验证；仅存于旧进程内存的登记不能证明重启恢复。不要编造无关的生命周期场景。

当 teardown、migration 或 commit 包含多个可能失败的效果时，默认把部分失败和重试视为实质风险。只有证明这些效果是原子或不会失败后，才能省略该转换；否则必须验证：只有在清理达到安全状态后，才释放所有权和计量。

把跨持久化或外部效果的操作写成有序时间线，在每个不可逆边界前后询问一次进程退出会留下什么。尤其不要把“attempt 已递增”“checkpoint 已推进”“状态已标记为处理中”当作外部调用、提交或清理已经发生的证明。恢复逻辑必须区分尚未发生、可能发生和已确认发生。

取消必须先让调用方及时收口。若底层读取、发送或 handler 永久悬挂，清理动作不能通过等待同一个悬挂操作而反过来阻塞取消；应启动可行的关闭，界定无法等待的残余，并用悬挂操作探针证明 prompt cancellation。

可行时，在实际目标上复现平台或配置特定故障。宿主环境构建成功，不能证明失败目标已经正确。

## 6. 证明机制和完整性

让检查具备推翻修复的能力。可行时，在修改前观察原始故障，或先看到回归检查失败。

证明结果由预期机制导致。当环境保护、调度、时间或选择范围也可能解释结果时，控制这些因素或断言它们的状态。当宽泛选择器或破坏性清理可能触及无关状态时，加入负向对照（negative control）。让诱饵进入与所属目标相同的候选域，并且只在所有权或受保护属性上不同；同时覆盖“同一目标在认领前已存在”的碰撞，证明它不会被错误接管。完全不匹配选择器的对象不能推翻“选择器过宽”。名称或前缀本身不构成所有权证明，因为外部对象可能使用同一命名形式；使用登记集合、不可混淆的命名空间令牌、元数据或等价的独立信号选择所属对象。该信号必须比它负责恢复的故障边界更持久：用于重启后 sweep 的信号不能只存在于重启前的进程内存。若不存在可信且足够持久的信号，将清理完整性标为受阻或残余项，不得宣称闭环。若无关宿主设置变化就会改变结果，机制尚未得到证明。

当部分成功可能呈现为全绿时，枚举完整闭合集合：所有待释放资源、待更新消费者、待保护协议跳转、待重置状态投影或待编译目标。将聚焦因果检查与能够发现回归的最小范围套件配对。不要用无关的绿色检查替代受阻证据。

## 7. 关闭实质性发现

根据请求、真实路径和验收门槛审查最终 diff 与行为。当使用完整路径且影响范围值得独立性时，若有可用审查者，执行独立冷审（cold review）：只提供原始任务和工件，不提供预期答案或疑似缺陷清单。若无法获得独立审查，则从验收门槛出发进行一次刻意的第二遍检查，并说明未执行独立审查；不要虚构审查，也不要因此阻塞。

第二遍检查必须尝试推翻第一次的模型，而不是重读同一成功路径。根据风险从诊断中的边界反例扫描选择不同视角：表示或 schema 碰撞、外部效果前后的崩溃窗口、特殊资源类型与身份竞态、悬挂操作、迁移 source 变化、能力域外输入，或题目声明规模下的 I/O 次数。若没有相关视角，明确说明为何现有门槛已经覆盖，而不是机械增加检查。

当一个发现可能违反需求或验收门槛，引入安全、完整性、数据丢失、兼容性或生命周期回归，或使已声明证据失效时，将其视为实质性发现（material finding）。修复每个有证据支持的实质性发现，补充或加强暴露该问题的检查，并重跑受影响证据。重复这一过程，直到没有实质性发现，或明确记录真实阻塞项、由用户明确接受的残余项。

约束循环次数。细枝末节、风格偏好和反复出现但无证据支持的担忧，不足以支持无限审查。独立性和可证伪性比审查者数量更重要。

## 8. 报告证据，而非信心

报告实际变更和已证明的验收门槛，并明确区分：

- 实际运行的自动化检查；
- 实际执行的人工或目标环境验证；
- 受阻或未运行的检查；
- 已知残余项、延期工作和明确的非目标。

不要把这些类别合并成一句“已验证”。把每个实质性门槛解析为：已证明、受阻、原请求范围之外，或已由用户或责任所有者明确接受。代理可以提出残余项，但不能自行接受实质性残余项。允许在有价值时部分交付，但实质性门槛仍受阻或未被接受时，不得宣称完整闭环。如果项目已有事实来源，应把持久决策或变化后的不变量记录到该来源中。
