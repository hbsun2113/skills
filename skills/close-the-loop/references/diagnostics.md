# 闭环诊断

只在完整路径中读取本文：高风险规划、实现审查，或跨越信任、持久化、共享状态、多消费者、生命周期或目标特定行为的任务。常规多步骤修改不会自动成为完整路径任务；未命中完整路径触发器但不满足轻量条件时，按 `SKILL.md` 的标准路径执行。只使用与已观察风险相关的任务路线和矩阵行。

## 任务路线

证明项是按已观察风险选择的菜单，不是累积清单。只运行能够推翻变更契约的相关转换或对照。

| 路线 | 编辑前先确定 | 针对风险的证据 | 规则 |
| --- | --- | --- | --- |
| 故障修复 | 真实故障信号、因果路径、责任边界、受影响消费者 | 原始故障或失败的回归检查；修复后的路径；聚焦回归 | 1, 2, 3, 6 |
| 有状态或并发变更 | 状态所有者、合法转换、时序假设、陈旧状态来源 | 控制因果路径涉及的重排、取消、重试、重启或并发场景；断言相关最终状态 | 1, 2, 5, 6 |
| 安全或完整性边界 | 受保护资产、攻击者可控转换、策略来源、绕过路径、恢复行为 | 在效果边界验证允许和拒绝场景；只有环境防御可能掩盖决策时才控制它；说明残余项 | 2, 3, 4, 5, 6, 8 |
| 重构或迁移 | 当前与替代路径、契约、所有消费者、回滚或并存边界 | 允许并存时验证安全既有行为等价性；否则保护或禁用不安全路径；枚举消费者；提供旧路径退役证据 | 1, 2, 3, 6 |
| 平台或 CI 故障 | 精确目标、失败作业或命令、平台条件行为 | 目标特定编译或执行；宿主检查单独报告 | 1, 2, 5, 6, 8 |
| 资源生命周期 | 资源清单、所有者、排他认领机制、独立于名称且能跨越目标失败边界的所有权信号、分配与释放顺序，以及选择相同资源的每条 teardown、recovery 和 sweep 路径 | 正常清理；认领前同路径碰撞不得被接管；多个可能失败的释放步骤发生部分失败后的重试；仅在安全清理后释放计量；重建所有者或清理器后验证恢复；选择范围宽泛或具破坏性时，证明进入相同名称候选域但没有所有权信号的外部诱饵存活 | 1, 2, 3, 4, 5, 6 |

## 闭环矩阵

无法回答的实质性行就是一个发现。用证据解决它，将它标为受阻，或请求用户或责任所有者把它明确接受为残余项。代理不能默默接受，也不能用看似合理的文字填补空白。

| 槽位 | 问题 | 规则 |
| --- | --- | --- |
| 真实路径 | 哪个当前入口、所有者、转换、消费者和恢复路径产生了观察到的行为？重新检查了哪些继承假设？ | 1 |
| 门槛 | 哪个可观察属性一旦为假就应阻止交付？哪些负向、恢复、回归和仅人工检查相关？ | 2 |
| 边界 | 不变量是否由最接近效果的所有者强制执行？是否追踪了每个消费者和每层防御的不同职责？ | 3 |
| 失败 | 哪些错误必须传播，哪些输入或等待需要边界，何处必须故障时拒绝而不是明确失败？ | 4 |
| 时间轴 | 乱序、重复、并发、取消后、失败中途、跨重启和清理期间分别会发生什么？ | 5 |
| 因果性 | 检查能否在旧行为上失败？宿主策略、时序、另一层防御或未经断言的前置条件能否解释绿色结果？ | 6 |
| 完整性 | 哪个有限的资源、消费者、跳转、状态副本或目标集合必须完整枚举而不是抽样？ | 6 |
| 审查 | 冷审是否收到原始工件？有证据支持的实质性发现是否修复并重跑检查？停止条件是什么？ | 7 |
| 证明 | 哪些证据属于自动化、目标特定、人工、受阻、未运行、残余或范围外？最终声明是否保留这些区别？ | 8 |

## 边界反例扫描

只选择与真实路径相关的行。此表用于在第二遍检查中寻找第一次模型没有表达的反例，不是要求每个任务执行所有探针。

| 风险信号 | 用于推翻模型的问题 | 典型证据 |
| --- | --- | --- |
| 表示、解析或 schema 边界 | 省略、`undefined`、`null`、falsy、非法编码和合法但碰撞的标记值是否被区分？是否仅凭一个普通业务字段就把旧数据识别为新 envelope？ | 严格解码；显式 `null`；未知字段与 schema 标记同值的 legacy 对照；完整结构和版本识别 |
| 持久状态后接外部效果 | 如果在持久化 attempt/checkpoint/`in_progress` 之后、真实发送/提交/清理之前退出，恢复会漏做还是重做？若效果已发生但确认未保存又如何？ | 在每个 durable/effect 边界前后注入退出；重建所有者；断言稳定幂等键和最终状态 |
| 取消与资源关闭 | 底层 `next()`、read、send、handler 或 `return()` 永久不完成时，取消是否仍及时？关闭是否排在同一个悬挂操作之后？ | 永不 settle 的输入或 handler；有界时间内观察取消；关闭尝试与调用方收口分别断言 |
| 文件系统对象与身份 | 路径可能是 FIFO、设备、socket、目录或被替换的符号链接吗？检查对象和使用对象是否相同？rename 后目录项是否满足所声明的持久性？ | 非普通文件；open 前后 inode/dev 复核；`O_NOFOLLOW`/等价边界；文件与父目录同步故障 |
| 值、句柄或能力快照 | 结构化复制失败后，是明确拒绝、只读代理，还是静默复用原引用或在下游才失败？冻结是否真的阻止 `Map`/`Set`/私有状态变更？ | 不可复制值和带内部槽对象；修改快照后检查存储结果；在效果前验证支持域 |
| 迁移与 staging | staging 是否绑定它转换的 source 内容或版本？中断后旧写入方更新 source 时，恢复会覆盖新值吗？标记、backup 和回滚路径是否可碰撞？ | staging 写入后中断；改变 canonical source；重启并断言新值保留；旧二进制回滚 |
| 声明规模与成本 | 机制在题目规模上每条记录、每次重试或每个资源执行多少同步 I/O、扫描或复制？正确但线性 fsync/平方扫描是否使方案不可用？ | 计数关键操作；代表规模基准；批次边界；把性能结果与功能证据分开报告 |

如果实现不支持某类输入或能力，应在最接近入口的验证边界明确拒绝并记录契约；不要静默复用可变引用、把合法旧数据误判为新格式，或让失败延迟到部分效果之后。

## 验收门槛模板

只有任务复杂到确实受益时，才使用精简表格。

| 风险 | 保护机制 | 可证伪检查 | 状态 |
| --- | --- | --- | --- |
| 哪些情况可能造成实质失败？ | 不变量应该位于哪里？ | 什么结果能够证明机制不存在或有误？ | open / proven / blocked / human |

每个门槛都必须影响交付决定。删除只是复述命令或文件修改的门槛。

## 审查循环

1. 根据请求、diff、真实路径、验收门槛、测试和已报告证据进行自审。
2. 对影响显著的工作，在有独立审查者时，基于原始任务和工件执行冷审；否则从验收门槛出发进行一次刻意的第二遍检查，并披露无法获得独立性。
3. 只有可能破坏需求、验收门槛、受保护边界、兼容性承诺、生命周期或证据声明的发现，才归为实质性。
4. 修复有证据支持的实质性发现，并补充缺失的因果或回归检查。
5. 重跑受影响检查；只有修复改变了实质风险面时，才重复审查。
6. 当没有有证据支持的实质性发现时停止；否则记录阻塞项，或由用户或责任所有者明确接受的残余项。不要为了制造确定感而反复处理细枝末节。

## 证据标签

在工作记录和最终报告中保留以下稳定标签，并用精确中文说明：

- `focused`：直接验证变更机制。
- `regression`：验证相邻或既有行为仍然有效。
- `target`：在曾经失败的平台、运行时或配置中执行。
- `human`：由人员实际操作并观察。
- `blocked`：相关但不可用，同时说明原因。
- `residual`：有意保留的已知行为或暴露面。
- `accepted`：由用户或责任所有者明确接受的实质性残余项；代理不得自行推断。
- `out-of-scope`：明确排除，且闭环声明不暗示其已完成。
